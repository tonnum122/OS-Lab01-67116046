1. The Deadlock (Phase 2):
ในสคริปต์ deadlock_simulation.py เกิดสภาวะ Circular Wait ตามลำดับดังนี้:
- ขั้นที่ 1: Model A รันและเข้าถือครอง gpu_0_lock สำเร็จ จากนั้นเข้าสู่สถานะรอ (Wait) เพื่อขอครอบครอง gpu_1_lock
- ขั้นที่ 2: ในเวลาเดียวกัน OS ทำการ Context Switch ให้ Model B รันและเข้าถือครอง gpu_1_lock สำเร็จ จากนั้นเข้าสู่สถานะรอ (Wait) เพื่อขอครอบครอง gpu_0_lock
- ขั้นที่ 3: Model A ไม่ยอมปล่อย GPU 0 จนกว่าจะได้ GPU 1 ส่วน Model B ก็ไม่ยอมปล่อย GPU 1 จนกว่าจะได้ GPU 0 ทำให้เกิดการรอคอยทรัพยากรแบบเป็นวงกลม (Circular Wait) ครบเงื่อนไขทั้ง 4 ข้อของ Coffman ส่งผลให้โปรแกรมค้างถาวร (Deadlock)

2. The Solution (Phase 3):
การปรับโค้ดใน deadlock_avoidance.py ให้ Model B ขอครอบครอง GPU 0 ก่อน GPU 1 (ใช้ลำดับเดียวกันกับ Model A) เป็นการใช้หลักการ Resource Hierarchy / Lock Ordering ซึ่งทำลายเงื่อนไข Circular Wait เพราะ:
- จะมีเพียง Thread เดียวเท่านั้น (ระหว่าง Model A หรือ Model B) ที่แย่งเข้าถือครอง GPU 0 ได้ก่อน
- Thread ที่ได้ GPU 0 ไป จะมีสิทธิ์รันต่อและขอ GPU 1 จนทำงานเสร็จสิ้น แล้วจึงปล่อย Lock ของทั้ง GPU 0 และ GPU 1 คืนให้ระบบ
- อีก Thread หนึ่งจะติดรออยู่ที่ GPU 0 ตั้งแต่แรก ทำให้ไม่มีเหตุการณ์ที่ต่างฝ่ายต่างถือครองทรัพยากรคนละชิ้นแล้วรอซึ่งกันและกัน วงจรการรอแบบ Circular จึงถูกทำลายลงอย่างสมบูรณ์

3. Starvation vs Deadlock (Phase 4):
- ความแตกต่างของผลลัพธ์: ใน Deadlock ระบบจะหยุดนิ่งโดยสิ้นเชิง (Freeze) และไม่มี Process ใดทำงานคืบหน้าได้เลย แต่ใน Starvation ระบบยังคงทำงานต่อเนื่อง (System is running) โดยกลุ่ม Greedy Models สามารถเข้าแย่ง Lock ทำงานได้หลายหมื่นครั้ง ขณะที่ Polite_Model ยังคงมีชีวิตอยู่แต่ถูกแย่งทรัพยากรจนแทบไม่ได้รับโอกาสทำงาน (Indefinitely Denied)
- การทำงานของ Aging: เป็นเทคนิคที่ OS Scheduler จะค่อยๆ ปรับเพิ่มค่าระดับความสำคัญ (Priority) ของ Process ที่ต้องรอคอยอยู่ในคิวนานขึ้นเรื่อยๆ ตามเวลาที่ผ่านไป เมื่อ Polite_Model รอนานพอ Priority จะสูงขึ้นจนแซงหน้า Greedy Models ทำให้ได้รับสิทธิ์เข้าใช้ทรัพยากรอย่างเท่าเทียมและเป็นธรรม

4. Deadlock Detection & Recovery (Phase 5):
- การจำลองการตรวจจับด้วย timeout: พารามิเตอร์ `timeout=2.0` ใน `gpu_1_lock.acquire()` ทำหน้าที่เหมือน Watchdog Timer ของระบบปฏิบัติการ หากรอทรัพยากรเกิน 2 วินาทีแล้วยังไม่ได้รับ ระบบจะอนุมานว่าเกิดสภาวะ Deadlock หรือคอขวดขึ้น
- การทำ Recovery ของ Model A: เมื่อหมดเวลา Timeout และไม่ได้รับ GPU 1 ตัว Model A จะทำ Rollback / Resource Preemption ด้วยการเรียกคำสั่ง `gpu_0_lock.release()` เพื่อปล่อย GPU 0 คืนกลับสู่ระบบ ทำให้ Model B ที่กำลังรอ GPU 0 อยู่ สามารถคว้าทรัพยากรไปประมวลผลต่อจนจบงาน ช่วยให้ระบบทำงานต่อไปได้โดยไม่ค้าง
